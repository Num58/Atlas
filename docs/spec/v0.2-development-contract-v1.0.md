## 1. 目标、成功条件与版本锚定

### 1.1 研发目标

交付一个可在 Android/iOS Flutter 应用内、完全断网运行的 V0.2 闭环：

```text
价值预览/游客继续
  -> 表达目标方向、时间、场景与现实约束
  -> 编辑并显式确认目标边界
  -> 选择 1–3 个活跃成长域
  -> 创建、编辑并确认域内目标
  -> 创建或确认里程碑
  -> 查看旅程总览、目标详情、目标边界版本历史和本机保存状态
  -> 杀进程重启后仍恢复为同一 owner、版本和已提交事实
```

成功必须同时满足：

1. 范围内主流程和关键错误流可运行；
2. 所有写入通过共享 SQLite Unit of Work 原子提交；
3. owner 隔离、乐观锁、幂等账本、事件与审计合同成立；
4. 断网不降级核心闭环，业务网络调用为 0；
5. 范围外路由、入口、业务对象和外部 Port 调用为 0；
6. 功能图标只通过 ADR-009 的 `AppIcon` 使用 Lucide SVG allowlist；
7. format、analyze、unit、integration、contract、platform gates 达到本文门槛。

### 3.3 文件组织硬规则

- 一个 Dart 源文件一个主职责、一个主导出；源文件不超过 300 行。
- `main.dart` 与 bootstrap 只装配，不写领域规则、SQL、路由页面实现或 fixture 数据。
- 页面只做输入校验、调用 application、渲染不可变 UI state；不得直连 SQL/Repository。
- application 负责业务用例与 UoW 编排，不 import Flutter widget 或 sqlite3。
- core 纯 Dart，不 import Flutter、sqlite3、path_provider 或平台 plugin。
- Repository 只做 owner-scoped 数据读写和映射；状态转换、上限、分类与确认规则由 core/application 决定。
- 跨功能调用经 application facade/core Port，不跨模块直连对方 Repository。
- JSON 键、数据库表/列、事件字段为 `snake_case`；Dart 枚举可 camelCase，但必须有明确 code 映射。

## 4. 页面与路由冻结

### 4.1 一级入口

V0.2 一级入口仅两项：

| Route ID | Path | 导航标签 | 责任 |
|---|---|---|---|
| `journeyRoot` | `/journey` | 旅程 | 方向、现实约束、成长域、目标、里程碑和旅程总览的唯一业务主入口 |
| `meRoot` | `/me` | 我的 | 目标边界版本历史、本机数据状态和主体基础说明 |

根路径 `/` 必须确定性重定向到 `/journey`。不得注册 Today、训练、Pulse、Knowledge、连接、权限或同步路由。终局扩为四入口时保留 `journeyRoot`、`meRoot` 的 route name、对象 ID 和返回语义。

### 4.2 范围内路由清单

以下 route name/path 是 V0.2 实现合同；同一对象不得另造第二套可编辑页面。

| Route name | Path | 页面/职责 | 主要消费 |
|---|---|---|---|
| `journeyRoot` | `/journey` | 旅程总览；无数据时给出开始方向表达的明确入口 | UC-019a |
| `journeyPreview` | `/journey/preview` | 内置只读价值预览；不写用户对象 | 本地静态内容 |
| `directionDiscovery` | `/journey/direction/discovery` | 自由表达目标、时间、场景和现实约束；可提前结束 | UC-001/002 |
| `directionDraft` | `/journey/direction/draft/:draftId` | 编辑、提交或丢弃草案 | UC-002/003/005 |
| `directionConfirm` | `/journey/direction/confirm/:draftId` | 显式确认目标边界；不得默认确认 | UC-004 |
| `domainSelection` | `/journey/domains` | 激活/暂停/恢复/归档 1–3 域；第 4 域显示聚焦建议 | UC-008/009/010 |
| `goalList` | `/journey/goals` | 按 active domain 查看多个目标及状态 | UC-019a |
| `goalCreate` | `/journey/goals/new` | 本地手工/规则目标草案，不调用远程生成 | UC-011 |

| `localDataStatus` | `/me/local-data` | 本机保存、错误、迁移只读恢复状态；不显示云同步 | UC-020/启动状态 |

`/journey` 可以提供指向 `/me/boundary-versions` 的兼容交叉入口，但不得复制版本编辑/恢复页。

### 4.3 路由与返回语义

- 两个一级入口各自保留导航栈；再次点击当前一级入口回到其 root。
- 完成方向确认后使用 replace/go 进入 `/journey/domains`，返回不得重新提交已完成 operation。
- 从旅程进入目标详情使用 push；保存/取消后 pop 回原旅程上下文。
- 从目标详情进入里程碑使用 push；返回仍回同一 `goalId`。
- 恢复历史版本成功后 replace 到 `/journey` 并展示新 active 版本结果，不返回旧表单继续写。
- 未知、范围外或非法深链显示本地 not-found 页面，并提供回 `/journey` 的明确动作；不得动态创建范围外页面。
- 路由参数只承载 ID，不承载可被篡改后直接写库的 owner、状态或完整对象。
- owner 由当前本地主体上下文提供，不从 URL/query 获取。

### 4.4 页面状态最低合同

所有范围内页面都必须显式建模并可测试：initial/loading/empty/ready/saving/savedLocal/validationError/storageError/versionConflict/readOnlyRecovery。另按页面覆盖：

| 页面族 | 必须状态 | 禁止 |
|---|---|---|
| 方向发现/草案 | 首次、部分数据、保存中、本机已保存、保存失败、离线、stale version | 丢编辑缓冲、身份定义、无限 spinner |
| 方向确认 | pending、确认中、confirmed、数据不足、版本冲突 | 默认确认、系统自动确认 |
| 成长域 | 0 域草稿、1–3 active、第 4 域聚焦建议、paused、archived | 未激活占位、静默替换或删除 |
| 目标 | draft/pending/active/paused/recalibrating/completed/archived、数据不足、保存失败 | 未确认直接 active、精确伪指标 |
| 里程碑 | not_started/in_progress/achieved/not_achieved/superseded、依赖缺失 | 缺规则仍确认、失败羞辱 |
| 旅程 | 单/双/三域、空、暂停/归档、读取失败 | 卡片墙、重复编辑真源、Today 行动 |
| 版本历史 | 空历史、active/superseded、恢复确认、恢复成功/冲突 | 原地覆盖历史、身份画像产品文案 |
| 本机数据 | savedLocal、rejected、storage failed、migration read-only | “已同步云端”“待同步”或远端进度 |

错误页必须提供标题、错误摘要、可执行恢复动作、读屏播报和可预测回焦；不得直接显示 SQLite 原始异常文本。

## 5. 状态管理与运行时边界

### 5.1 Riverpod 边界

- UI 可变状态使用不可变 state；复杂异步流程使用 `Notifier/AsyncNotifier`。
- Provider 只依赖 application facade/use-case，不直接暴露 Database 或 Repository 给页面。
- Provider 状态只保存呈现所需数据、表单编辑缓冲和异步状态；持久业务事实只来自 application/repository 查询结果。
- owner、Clock、IdGenerator、UnitOfWork、外部 Port 均通过 composition root 注入，不使用可变全局 singleton。
- 页面销毁不得清掉尚未成功持久化的编辑缓冲；保存失败允许用户修正/重试/返回。
- 不使用 FutureProvider 触发写操作；mutation 必须由明确用户动作调用 notifier 方法。

### 5.2 启动状态机

```text
uninitialized
  -> openingDatabase
  -> checkingIntegrity
  -> migrating
  -> ensuringLocalSubject
  -> ready

任一步失败：
  recoverable storage busy/full -> failedWithAction
  corrupt/readonly/migration/unknown higher schema -> readOnlyRecovery
```

只有 `ready` 开放写路径。`readOnlyRecovery` 允许读取可安全读取的本机事实、查看错误说明和退出/重试受允许动作；禁止删库重建、伪装迁移成功或开放写入。

## 6. 数据、Repository 与 Unit of Work 合同

### 6.1 物理 Schema 真源

V0.2 baseline 真源是：

`lib/infrastructure/storage/sqlite/migrations/0001_baseline.sql`

它包含 12 个业务/基础表加 `schema_migrations`：`subjects`、`devices`、`identity_drafts`、`portrait_candidates`、`portrait_versions`、`active_domains`、`goals`、`milestones`、`evidence_links`、`domain_events`、`audit_records`、`operation_ledger`。V0.2 无 `tombstones`。

硬规则：

- `PRAGMA foreign_keys=ON`、WAL、`synchronous=FULL`、`busy_timeout=1000`；
- 所有用户表含 owner，父表 `UNIQUE(owner_id,id)`，子表使用复合 owner 外键；
- UUIDv7 小写带连字符 TEXT；业务时间用 UTC 微秒，并保留 timezone/offset；
- JSON 写入前 canonicalize，hash 为 SHA-256 小写十六进制；
- 历史和追加事实禁止 `INSERT OR REPLACE`；
- migration 编号不可变，已应用文件 checksum 不得漂移；
- 未知更高 schema 只读，失败不得删库重建。

Migration checksum 在首个正式 migration 发布前统一锁定为 SHA-256，禁止继续使用 FNV-1a 64。输入为 migration SQL 文本经以下 `migration-sql-v1` 规范化后的 UTF-8 字节：移除开头一个 U+FEFF BOM；将 CRLF 和单独 CR 统一为 LF；其余字符、空白与末尾换行保持不变。输出固定为 **64 个小写十六进制字符**，不含 `0x`、算法前缀、Base64 或分隔符。Runner 写入前和读取 ledger 时均须校验 `^[0-9a-f]{64}$`；同 version/name 但 checksum 不同必须 fail-closed 为 `local_migration_failed`，不得改写已应用 ledger。实现使用精确锁定的 `package:crypto`，不得自研哈希；`crypto` 必须列为 direct dependency。当前 FNV 实现是在本条款明确前产生，属待收口实现而非追溯违约；因为尚未形成正式已发布 migration ledger，应立即切换，禁止为兼容未发布 FNV ledger 引入双算法分支。

### 6.2 Repository Port

V0.2 只实现以下 Port；所有方法首参必须是 `OwnerId ownerId`，SQL 首要谓词包含 owner：

| Port | 责任 |
|---|---|
| `SubjectRepository` | current、bindGuest、switchSubject；V0.2 只创建本地 guest |
| `IdentityRepository` | get/save draft、active boundary version、versions、append candidate、activate version |
| `DomainRepository` | list active/all lifecycle、get、save version |
| `GoalRepository` | get/list/save goal version、list/upsert milestones、journey read projection |
| `EvidenceRepository` | link、invalidate、list by object |
| `AuditRepository` | append、list by object/operation |
| `OperationLedgerRepository` | find owner+operation、record committed/rejected、replay exact result |
| `LocalPersistenceRepository` | transaction、CAS、consistent read、integrity/schema state |

不实现 `SyncRepository`、`TombstoneRepository` 或远程 Repository。

### 6.3 共享 Unit of Work

所有写 Use-case 必须共用同一 `PrimeAtlasDatabase` connection，并在单一 SQLite transaction 中按下列顺序执行：

```text
1. 查询 (owner_id, operation_id) 幂等账本
2. 同 operation + 同 payload_hash：返回原 committed/rejected 结果，零新副作用
3. 同 operation + 不同 payload_hash：拒绝 idempotency_key_reused，零副作用
4. 校验 owner、base_version、状态、字段和业务规则
5. 写聚合/版本
6. 追加 domain_events
7. 追加 audit_records
8. 写 operation_ledger committed 或确定性 rejected
9. COMMIT
10. commit 后再通知内存 subscriber；subscriber 失败不回滚已提交事实
```

本地存储故障发生在任一写点时整笔 ROLLBACK，且不得尝试另写 `rejected` ledger。确定性业务拒绝可写 rejected ledger；读取用例不接触 operation ledger。

目标边界确认必须原子完成：draft confirmed、新 active `portrait_version`、旧 active superseded、事件、审计、committed ledger。`archiveDomain` 必须原子完成 domain archived、关联 active goals paused、事件、审计和 committed ledger。

### 6.4 幂等、并发与读取

- `(owner_id,operation_id)` 唯一；同 hash 重放返回原 `result_json`，不重复事件。
- mutation 除 create 外必须带 `baseVersion`，更新用 `WHERE owner_id=? AND id=? AND version=?` CAS。
- stale version 返回 `version_conflict`，不得 last-write-wins。
- `getJourneyOverview` 使用 `(updated_at_us,id)` 两列 DESC keyset cursor；默认 20，范围 1–100。
- `getGoalDetail` 在 ID 存在但 owner 不同的情况下返回 `account_ownership_mismatch`；同 owner 不存在才 `not_found`。
- 查询在一致 SQLite 只读事务内完成，不接收 operationId。

### 6.5 Application Use-case 边界

唯一业务语义沿用 `UC-001..021`，其中 `UC-021` 只为冲突注入测试 Port，不进入生产路由。实现不得改写 `v0.2-freeze-gap-plan-v1.0.md` §4.2 已冻结签名/结果。

特别约束：

- `UC-004 confirmIdentityDraft` 仅用户显式动作可成功；
- `UC-008 activateDomain` 第 4 域返回确定性 `FocusSuggestion` 且无写入；
- `UC-010 archiveDomain` 需要匹配当前影响摘要 SHA-256；归档不是删除；
- `UC-011 createGoalCandidate` 仅本地手工/规则，不调用 RemoteDiscovery/AI；
- `UC-013 updateGoal` 小改保持状态并 version+1；重大改动进入 recalibrating；未知/不可唯一分类不写入；
- `UC-019a/b` 是只读事务，无 operation ledger；
- `UC-020` 文案为本机保存状态，不是同步状态。

### 6.6 错误与恢复矩阵

`DomainFailure` 固定形状：`code, retryable, messageKey, details, expectedVersion?, actualVersion?`。UI 只显示 messageKey 对应的明确产品文案。

| 错误码 | retryable | 自动动作 | 用户动作/页面恢复 |
|---|---:|---|---|
| `validation_failed` | false | 定位字段 | 修正输入；焦点移到错误摘要/首字段 |
| `data_insufficient` | false | 保持 draft/exploratory | 补充信息或保留探索态 |
| `invalid_state_transition` | false | 重新查询当前状态 | 返回合法页面，不重复写 |
| `version_conflict` | false | 读取 current/base 快照 | 并列展示来源和影响，由用户解决 |
| `idempotency_key_reused` | false | 保留原 operation 结果 | 为新意图生成新 operationId |
| `account_ownership_mismatch` | false | 终止访问 | 回当前主体根页；不得泄露他方数据 |
| `not_found` | false | 不猜测对象 | 回旅程并刷新列表 |
| `domain_focus_required` | false | 返回 FocusSuggestion | 用户暂停/归档现有域或取消 |
| `impact_confirmation_required` | false | 刷新影响摘要/hash | 重新确认当前影响 |
| `change_classification_required` | false | 零写入 | 用户拆分或明确变更 |
| `local_store_busy` | true | 内部最多 3 次，总计不超过 1 秒 | 仍失败时手动重试 |
| `local_store_full` | 条件 true | 不自动循环 | 释放空间后手动重试；编辑缓冲保留 |
| `local_store_readonly` | false | 进入只读恢复 | 查看说明/兼容数据；不开放写 |
| `local_store_corrupt` | false | 进入只读恢复 | 不删库；保留诊断与恢复入口 |
| `local_migration_failed` | false | 回滚并保留备份 | 只读恢复；允许安全重试迁移 |
| `local_transaction_failed` | false | 整笔回滚 | 保留编辑缓冲，重新发起新操作 |
| `unexpected_external_call` | false | 测试立即失败 | 生产不应可达；作为 Release blocker |

## 7. Migration 与本地恢复

### 7.1 MigrationRunner 合同

启动流程固定为：

```text
读取 user_version/schema_migrations
  -> 校验已应用 migration checksum
  -> PRAGMA integrity_check/foreign_key_check
  -> 创建 pre-migration 备份（文件数据库）
  -> BEGIN IMMEDIATE
  -> 顺序执行待应用 migration
  -> 记录 version/name/checksum/applied_at_us/app_version
  -> foreign_key_check
  -> COMMIT
  -> 开放写路径
```

失败必须 ROLLBACK，保留原 DB 与备份，进入只读恢复；禁止删除数据库再建。V0.2 支持当前 schema 和 N-1 升级；未知高版本只读。修复使用 forward-only 新 migration，不修改已发布 `0001_baseline.sql`。

### 7.2 运行时数据库生命周期

- 正式 runtime 只创建一个受控 `PrimeAtlasDatabase` 实例。
- 所有 Repository/UoW 从该实例获得 connection/transaction context。
- 测试每例使用唯一临时 DB 或 in-memory DB，不共享 singleton。
- teardown 必须关闭连接并删除临时目录。
- 生产 DB 路径由平台目录适配器提供，不硬编码开发机绝对路径。
- 日志不得打印 payload 原文、目标/约束全文或跨 owner 数据。

2. 执行 format、analyze、全部 unit/integration/architecture/schema tests。
3. 在全新临时数据库启动正式 App：创建本地 guest -> 价值预览 -> 方向/约束表达 -> 保存/编辑 -> 显式确认 -> 选择 1–3 域 -> 创建并确认目标/里程碑 -> 旅程 -> 目标详情 -> 我的目标边界版本。
4. 杀进程并重启；断言 current owner、active 版本、域、目标、里程碑、事件、审计和 operation ledger 一致。
5. 在确认事务各写点注入失败，并注入 `SQLITE_FULL/BUSY`；断言事务零半写、编辑缓冲保留、存储错误不产生 rejected ledger。
6. 同 operation 同 payload 重放，断言只一次副作用；同 operation 不同 payload，断言 `idempotency_key_reused`。
7. 用 owner B 读取/更新 owner A 对象，断言 `account_ownership_mismatch` 且双方 checksum 不变。
8. 验证第 4 域、impact hash 过期、Goal 分类不明确、stale baseVersion 和非法 Journey cursor/limit。
9. 导出 route registry、feature registry、semantics tree、SQLite table list、依赖/import scan 和 ThrowOnCall report；断言范围外入口/对象/调用为 0，baseline 无 tombstone。
10. Android 与 iOS 正式 runner 断网复跑核心流，归档 release build、Lucide asset/golden、a11y 与 HAR 0 业务请求证据。
11. `git diff --check` 为 0，required checks 无 bypass，非作者 reviewer 批准后才可合并 Release PR。
